# Application audit, 7 October 2026

## Scope and verified environment

Reviewed the TypeScript backend, persisted settings versions 1 and 2, Flow registration and tags, timer lifecycle, SunCalc integration, Compose definitions, and the separate Vue/Vuetify settings application. The settings source is `settings-src`; its generated distribution is `settings/`. The UI imports shared backend modules from `.homeybuild`, so compile the backend before building the UI.

Local environment: Node 24.15.0, Homey CLI 4.5.3, TypeScript 7.0.2, SDK types 0.3.12, Luxon 3.7.2 and SunCalc 2.1.1. Node types now target Node 22, matching Homey's current documented runtime. This preserves CommonJS rather than changing the Homey app to ESM.

## Corrections

| Area | Finding and correction |
| --- | --- |
| Compilation | TypeScript 7 removes `baseUrl` and changes compiler defaults. Removed the unused option, configured Node16 module resolution, explicitly retained the previous non-strict checking behavior and Node globals, and prevented emission after compilation errors. |
| Entrypoint | Corrected package `main`; verified the generated entrypoint directly exports the class extending `Homey.App`. |
| Root dependencies | Removed unused root ESLint, webpack and module-alias tooling and their unused configuration. Root compilation uses TypeScript; Vue tooling belongs to its separate package. |
| Settings build | Replaced Vue CLI 4/webpack 4 with compatible Vue CLI 5/webpack 5, resolving Node 24's OpenSSL hashing failure. Kept Vue 2/Vuetify 2, updated their compatible versions, and matched Vue/compiler versions exactly. |
| Settings bootstrap | Define the global callback before loading `/homey.js`, retain early callbacks, mount once, register currency controls before mount, and signal readiness independently of optional data loads. |
| Settings API | Use documented callback forms through small Promise wrappers; select the locale through the supported `Homey.__` interface. |
| Settings writes | Validate normal edits and raw imports before persistence. Reject malformed JSON, unknown versions, invalid IDs/types/times/event names, and invalid token values. Failed loads disable normal Save; a valid raw import remains available for repair. |
| Deserialization | Report invalid data instead of returning success or exposing partially read settings. Preserve working schedules after a bad reload and preserve invalid stored data for manual repair after startup. Both existing settings versions remain readable. |
| Reload lifecycle | Serialize settings reloads, catch listener errors, remove the listener on app unload, and cancel the active timer. |
| Timer lifecycle | Use Homey's timer APIs with a generation guard. An old callback or pending token write cannot restart a cancelled timer or dispatch a cancelled Flow. Consume failed executions once and log the underlying error. Refresh at day changes and retain midnight events. |
| Random windows | Cache one sample per schedule item and nominal Homey date across midnight, preventing duplicate or missed occurrences caused by re-sampling. Retain only adjacent dates and clear samples after settings replacement, timezone changes, or restart. |
| Flow tags | Match tags by their existing schedule-plus-token IDs, propagate tag-write and Flow failures, and pass the declared trigger's token object separately from schedule state. |
| Solar calculations | Use Homey's civil day and timezone, retain the solar instant and offset, normalize absent polar events to invalid dates, and register custom solar phases once. Unavailable before/after conditions skip execution. |
| Shared model | Correct reversed new-item time/event arguments, preserve monthly day masks, and return correct results from deletion/token-setter helpers. |
| Vue controls | Guard solar views until data is available, render solar times in Homey's timezone, emit validity changes without assigning the validity prop, and fix the disabled-button typo and stray template character. |
| App API | Supply the missing handler for the already declared read-only `GET /getScheduleState/` endpoint; it returns schedule `id`, `name`, and configured `active` state. |

## Compatibility and dependency limits

App ID, manifest version, `schedule_trigger`, its `schedule` argument, global tag IDs, settings keys, and settings formats remain intact. The `timezone` field added to cached geolocation is optional for existing UI data. No capability/device migration is required; this app has no drivers. Invalid data previously accepted silently now requires repair. SunCalc 2 uses newer astronomical calculations, so solar times can differ from SunCalc 1.

The configured Vue lint rule allows mutation of nested shared model objects while still rejecting replacement of prop references. This preserves the established component editing contract. Known Vuetify 2 Sass deprecation messages are explicitly silenced in its build configuration; this does not fix their underlying legacy syntax. Webpack bundle-size warnings remain.

Dependency audit results after compatible installation and `npm audit fix`:

- Root full and production dependency audit: zero vulnerabilities.
- Separate settings package: 42 findings, including development tools and frontend dependencies.
- Settings package with development dependencies omitted: three findings (Vue low, Vuetify high, and v-currency-field high through those dependencies). These are browser UI dependencies, not dependencies installed into the Homey backend runtime.
- Vue 2/Vuetify 2 remain legacy dependencies. Fixing every advisory requires replacing that component stack and the Vue CLI tooling. This change does not claim that the UI is vulnerability-free. No forced audit fix or peer-dependency bypass was used.

The Vuetify advisories cover prototype pollution and VDatePicker XSS; this application does not use VDatePicker. The Vue advisory concerns template parsing. Application templates are compiled during the local build; schedule values are not compiled as templates. These observations do not dismiss the audit findings or prove absence of all frontend exposure.

## Local verification

Commands for a clean checkout:

```powershell
npm ci
npm ci --prefix settings-src
npm test
npm run lint
npm run build:settings
homey app validate
homey app validate --level publish
git diff --check
```

Run build/test/Homey validation sequentially: Homey validation regenerates `.homeybuild`, which the tests and UI build consume. `npm run build:settings` regenerates `settings/` from Vue source; do not edit generated files manually.

Regression coverage exercises settings versions, invalid saves and loads, model constructors/helpers, schedule/tag identity, cancellation during asynchronous writes, Flow rejection, serialized reloads, unload cleanup, midnight and timezone handling, polar events, the API handler, CommonJS entrypoint, and callback-only settings bootstrap.

Executed results: 24 regression tests passed; Vue lint passed; backend and settings builds passed; both Homey validation commands passed at publish level; syntax and Git whitespace checks passed. Installed settings dependencies have no npm peer/tree problems. Generated asset references were checked, the original App.vue in the source map matches current source, and packaged settings HTML matches the regenerated distribution. The final UI build reports three bundle-size warnings.

Safe local checks cannot prove startup, settings rendering, tags, or Flow execution on a real Homey. No Homey installation, app run, publishing, device test, commit or push was performed.

## Manual Homey smoke test

1. Run `homey app run --remote` when ready to test this local change. Confirm startup finishes without an SDK, module, or API exception.
2. Open settings. Confirm the page becomes visible, existing schedules load, and number controls render correctly. Check the browser console for errors.
3. Save a valid time-based schedule and reload it. Add/delete a token and schedule item; confirm persisted data survives a restart.
4. Try malformed JSON, an unsupported version, an invalid time, and an invalid solar event in Raw settings. Confirm each shows an error and does not overwrite the saved data.
5. Switch to the solar tab immediately after opening settings. Confirm no null dereference occurs. Compare displayed dates/times with Homey's configured timezone, including a client using another timezone.
6. Use a disposable Flow with `schedule_trigger` and harmless observable output. Check time and solar triggers, before/after conditions, random windows, and global tag values.
7. Save settings several times while a trigger approaches. Disable/delete the schedule and confirm there is no duplicate or cancelled trigger. Check that one scheduler remains active after reload.
8. Restart before a future event and confirm it still fires once. Check a midnight event, negative/positive solar offsets, and a random window spanning midnight: its nominal occurrence must fire at most once and retain its sampled time during daily refresh. Past events remain skipped at startup; random samples are recomputed after restart or settings replacement and are not persisted.

Real Homey runtime behavior remains unverified until these tests succeed.
